Two known risks this task exists to resolve:

1. `COTRTUPC` pulls its DCLGEN copybooks in with `EXEC SQL INCLUDE DCLTRTYP
   END-EXEC`. `squall.preprocess.apply_sql_prepass` rewrites that to
   `COPY DCLTRTYP.` (`squall/squall/preprocess.py:125`), after which **ProLeap**
   must resolve it. The files are named `DCLTRTYP.dcl` and `DCLTRCAT.dcl` —
   extension `.dcl`, which ProLeap does **not** search by default. Its default
   list is `["", "cpy", "CPY", "cob", "cbl", "copy", "COPY"]`
   (`vendor/red-dragon/proleap-bridge/src/main/java/org/reddragon/bridge/Main.java:50-51`),

   plus `dcl`. `ProLeapCobolParser.__init__` already takes `copybook_exts`
   (`vendor/red-dragon/cobol_asg/cobol_parser.py:57`) — nothing in red-dragon
   needs changing, and no file staging or renaming is required.
2. `_load_field_meta` (`squall/squall/preprocess.py:130`) looks for a
   `DCLTRTYP.json` dclgen sidecar. CardDemo's copybooks are hand-written and
   have none, so field metadata will be `{}`. `build_sql_spec(..., tolerant=True)`
   exists for exactly this case.

in Tasks 3 and 6:

### Task 1b: squall's prepass must tolerate fixed-format sequence numbers — DONE (`forge-kgd`)

**Added after Task 1's gate failed.** ProLeap parses `COTRTUPC` fine — the
copybook extensions work — but squall's prepass never rewrites *any* of its
`EXEC SQL`, so the DCLGEN copybooks are never inlined and lowering dies with
`KeyError: "Field 'DCL-TR-TYPE' not found in any DATA DIVISION section"`.

Root cause, verified at the byte level: every file under
`app-transaction-type-db2/` carries fixed-format sequence numbers in columns
1-6, e.g. `028600      EXEC SQL INCLUDE DCLTRTYP END-EXEC`. The detector

```python
_EXEC_SQL_OPEN = re.compile(r"(?m)(^[^\S\n]*)(EXEC\s+SQL\b)", re.IGNORECASE)
```

(`squall/squall/preprocess.py:59`) admits only whitespace between start-of-line
and `EXEC`. Digits are not whitespace, so nothing matches and the file passes
through unchanged — silently. The rest of the CardDemo corpus has no sequence
numbers, which is why this never surfaced before.

This is a squall defect, not a CardDemo quirk: sequence numbers in columns 1-6
are ordinary fixed-format COBOL.

**Interfaces:**
- Consumes: nothing.

### Task 1c: strip `DECLARE TABLE` from real DCLGEN copybooks — DONE (`forge-9ow`)

**Added after Task 1's second gate run.** Task 1b's fix worked — the `EXEC SQL
INCLUDE`s now expand despite sequence numbers — but the gate moved to a new wall.

Both `DCLTRTYP.dcl` and `DCLTRCAT.dcl` carry the standard IBM DCLGEN preamble:

```cobol
     EXEC SQL DECLARE CARDDEMO.TRANSACTION_TYPE TABLE
     ( TR_TYPE                        CHAR(2) NOT NULL,
       TR_DESCRIPTION                 VARCHAR(50) NOT NULL
     ) END-EXEC.
```

`apply_sql_prepass` only ever sees the top-level source; ProLeap owns `COPY`
expansion, so this statement reaches its parser untouched and the grammar
cannot place an `EXEC SQL` inside a DATA DIVISION context:

```
syntax error in line 926:6 mismatched input '*>EXECSQL EXEC SQL DECLARE
CARDDEMO.TRANSACTION_TYPE_CATEGORY TABLE\n' expecting {... dataDescriptionEntryFormat1 ...}
```

squall's own `dclgen.py` emits only the host-variable record and never a
`DECLARE TABLE`, which is why this never surfaced: squall has only ever been
tested against its own synthetic copybooks, not real DCLGEN output.

A real Db2 precompiler consumes `DECLARE TABLE` and the COBOL compiler never
sees it. This task models that step.
