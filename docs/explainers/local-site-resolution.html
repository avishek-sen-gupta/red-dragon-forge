Resolving a dynamic call site inside its own program

Before any cross-program work, ask each program what its own dynamic XCTL, LINK, CALL, RETURN TRANSID and START sites can reach. Most can be answered from the program alone, and every one answered there stops costing the union of everyone's need.

Where this shows up in reverse engineering

On a large CICS corpus (about 3,800 programs and 19,000 jumps), the only goal was a call graph with the dynamic targets filled in. Those targets came in three shapes:

  • A literal VALUE in working storage, then EXEC CICS XCTL PROGRAM(WS-NEXT-PGM). Nothing ever writes the field.
  • A MOVE 'LITERAL' TO WS-FIELD, often one per branch of an IF or EVALUATE, then the call through the field.
  • A name read out of DFHCOMMAREA (about 5% of sites): a caller put the next program's name in the commarea, and this program XCTLs to it.

The first two shapes need nothing outside the program. Only the third needs the cross-program walk. The area-need stage decides which commarea bytes the fixpoint must track, and it was charging every dynamic site as if it were the third shape. Answering the first two locally stops those sites from being charged that union, so a program's row reflects the programs it really reaches.

The problem

Area need works out, per program, which bytes of a handed-over area the program's call targets depend on. At a call site that hands over an area, the caller must keep alive whatever the callee needs on entry. For XCTL PROGRAM('PROGB') that is PROGB's row. For XCTL PROGRAM(WS-NEXT-PGM) the callee is not known, so the only safe charge is the union of every member's entry row for that kind of area. In a corpus where some programs need thousands of bytes, that union is thousands of bytes, and it lands on every program with even one such site. It then spreads to their callers.

So: for each dynamic site, can we name every program it can reach, using only its own program? If yes, charge only those programs.

The intuition

Run reaching definitions forward over the program's control-flow graph, but carry the value set of one field only: the operand of the site. A write that overwrites every byte of the operand with a literal sets the set to that literal. A write that touches the operand any other way makes it unknown, and says why. Where paths meet, take the union. At the site, if every value is a literal, the site is resolved.

One doubt is let through: uninitialised. It means some path reaches the site with the operand never written and no VALUE. That storage belongs to this program, and no other program can have put a name in it. The site can reach only the names its literals spell.

The example

One program, three dynamic sites. PROGB, PROGC and PROGD each XCTL to a name in their own commarea: PROGB reads bytes 20–28, PROGC bytes 40–48, PROGD bytes 60–68. Nothing calls PROGD.

The three sites are on lines 24, 27 and 30. In cobble's node names they are MAIN-PARA/2.when.0.0, MAIN-PARA/2.when.1.0 and MAIN-PARA/2.when.2.0. The operands are WS-FIRST-PGM@working_storage[0:8], WS-MENU-PGM@working_storage[8:16] and WS-NEXT-PGM@working_storage[16:24].

Step by step

Each site gets its own walk, over its own operand. The three walks are shown side by side because they visit the same nodes. Each row is the set arriving at that node, which is what values_at returns for a site. Values are shown as stored: PIC X(8) pads 'PROGB' with three spaces, written ␣. The program has no loop, so the worklist visits each node once, in order.

Three forward walks over PROGA (7 steps)

  1. Entry. Each operand starts at what the program holds before any statement runs. WS-FIRST-PGM is covered by a VALUE, so it starts at that literal. The other two have no VALUE: uninitialised. An operand in LINKAGE would start as inbound-linkage.

    operandarriving
    WS-FIRST-PGM{'PROGB␣␣␣'}
    WS-MENU-PGM{} + uninitialised
    WS-NEXT-PGM{} + uninitialised

  2. IF WS-FLAG = 'Y' writes nothing. Both arms start from the same sets.

    operandarriving at each arm
    WS-FIRST-PGM{'PROGB␣␣␣'}
    WS-MENU-PGM{} + uninitialised
    WS-NEXT-PGM{} + uninitialised

  3. Each arm moves a literal into all eight bytes of WS-MENU-PGM. The write is exact, not weak, covers the whole operand, and its values are complete: it replaces. The then arm leaves {'PROGB␣␣␣'}, the else arm {'PROGC␣␣␣'}. The uninitialised doubt is gone on both: the write killed it.

    line 24 → PROGB

  6. Line 27: XCTL PROGRAM(WS-MENU-PGM). Arrives with {'PROGB␣␣␣', 'PROGC␣␣␣'} and no doubt. Resolved to PROGB and PROGC.

Other writes, one program each

Small programs, each ending in XCTL PROGRAM(WS-PGM) COMMAREA(WS-AREA) unless noted, run through the same stage. The reasons column is the site's; for the copy, the write's own reasons say something different, which the next section explains.

The rule

initial(o) = inbound-linkage, if o is in LINKAGE
           = the VALUE bytes covering o, if a VALUE covers it
           = uninitialised, otherwise
in(entry) = initial(o);  in(n) = ⋃ out(p) for every predecessor p
out(n) = in(n) after each write w at n:
  w misses o's bytes                                    → unchanged
  w replaces o (strong, exact, covers o, literal values) → w's values, sliced to o
  otherwise                                             → w's reasons − {uninitialised}, or not-a-literal if none remain

resolved(site) ⇔ o is one exact extent ∧ reasons(in(site)) ⊆ {uninitialised}
callees(site)  = program names among values(in(site)); none → resolved to nothing, no-program-name

transaction site: literal TRANSID → resolved to it; then through the CSD
  no CSD              → unresolved, no-csd
  id not in the CSD → that id reaches nothing; transaction-not-in-csd; still resolved

charge(site, slot) = ⋃ entry(c)[slot] for c in callees(site), if resolved
                       = ⋃ entry(m)[slot] for every member m, otherwise

A callee outside the corpus, or one that does not receive that slot, is charged every byte of the area. A site resolved to nothing is charged nothing.

Why uninitialised is accepted, and a copy is not

Uninitialised means one thing here: on some path, no write reached the operand and no VALUE covers it. That storage is this program's own working storage. No caller, callee or file put anything in it. So the only names the site can reach are the literals on the other paths. If that path really runs, the operand holds whatever the storage started as, not a name some other program chose.

A copy is different. The writes are computed once per program, without a state, so a MOVE WS-OTHER TO WS-PGM looks up WS-OTHER in an empty state and finds it "unwritten". That is a fact about the empty state, not about the program: WS-OTHER may well hold 'PROGB' by then, or a name read from a file. The walk does not follow the copy to find out. So the copy's uninitialised reason is dropped and the write is not-a-literal. In the --sites row above the copy's own reasons still show uninitialised, and the site's reason is not-a-literal. Accepting it would resolve the site to nothing and charge nothing, while the combine, following the copy, links it to PROGB.

A copy whose source carries a real reason keeps it: a copy out of LINKAGE is inbound-linkage, a LINK or CALL BY REFERENCE that hands the operand over is from-callee, a READ into it is from-file. A RETRIEVE INTO is modelled as CICS state with no literal: not-a-literal.

What goes wrong

  • One unresolved site is enough. In the example, two of three sites resolved, and PROGA's entry row is still 32 bytes, because line 30 alone pulls in the union. Local resolution shrinks a row only when it resolves every unresolved site that hands over that area.
  • A copy of a literal stays unresolved. MOVE 'PROGB' TO WS-OTHER then MOVE WS-OTHER TO WS-PGM is plainly PROGB, but the walk tracks one operand and does not follow copies. The site pays the union. The later cross-program walk does follow it.
  • Only one exact extent. An operand that could be several places, such as a subscripted WS-PGMS(I), gets operand-not-one-exact-extent and stays unresolved here, even though the combine can resolve it.
  • Conditions are not evaluated. A literal on a branch that never runs still counts. The site is resolved to more programs than it really reaches and is charged their rows too. That is loose, not wrong.
  • Values that are not program names. If no value looks like a program name, the site is resolved to nothing and charged nothing, with no-program-name. That matches the combine, which links such a site to nothing.
  • The walk starts at the program's entry. It assumes storage holds its VALUE or nothing on entry. A CALLed batch subprogram keeps its working storage between calls; a literal written after the site on an earlier call is not a reaching definition here. The value is still one of this program's literals, but the site's callees can miss it. (Read from the code; not reproduced.)
  • Without a CSD, transactions say so. A RETURN TRANSID or START without --config is unresolved with no-csd, not resolved to nothing. Resolving to nothing would charge nothing and drop the bytes the started program needs.

In cobble

The walk is values_at over a SiteGraph, built once per program, in site_values.py; it also decides what a write does to the operand (_replaces, _unknown) and what the operand holds on entry (_initial). local_sites.py picks the dynamic sites, accepts uninitialised and nothing else, names the callees, and maps transaction ids through the CSD. The result is a SiteAnswer; the doubts that are not value reasons are in site_doubt.py, and the value reasons in values.py. What each write carries comes from transfer.py.

prepared in area_needs.py runs it for each member before the rounds and splits the answers into resolved sites and unresolved ones. entry_at in area_table.py charges a site: its callees' rows when resolved, the union of every member's entry need otherwise. The --sites rows are SiteRow with SiteRowDefinition and DefinitionKind, written by area_need_cli.py. Sites a finished fixpoint and combine resolved are added from target_site.py. The command is documented under cobble-dataflow-area-need in field-dataflow.md.
