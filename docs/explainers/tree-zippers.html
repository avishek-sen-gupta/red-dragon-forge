Tree zippers

A cursor into an immutable tree that remembers the way back up, so editing one node deep inside does not mean redoing the walk that found it.

The problem

The tree never changes in place — a new node is built, never overwritten. So changing one node three levels down means building a new copy of it, then a new copy of its parent pointing at the new copy, then a new copy of its parent, up to the root. Nothing above the edit can be reused; the whole path has to be rebuilt.

Walking down to find the node in the first place already visits every statement on that path. Thrown away once the node is found, that walk has to happen a second time, backward, just to know which nodes need rebuilding. The zipper is what remembers the first walk, so there is no second one.

The tree

A small tree, four levels at its deepest:

Say the goal is to reach X and give it a sibling. In the diagrams below, amber marks the node currently in focus; a bordered node marks one remembered on the trail.

Going down: the trail grows

A zipper is two things: current, the node in focus, and trail, the ancestors passed to get there, nearest first. Moving down to a named child adds the node just left to the front of the trail.

Going up: free, because it was already remembered

Editing: rebuild on the way back up

The edit itself is ordinary: give the node in focus a new list of children. What happens next is the part worth watching. From A1, giving it a second child Y alongside X. The diagrams below mark the newly built node that is current amber, and any node built earlier in the same step but no longer current with a border.

Three new nodes — A1, A, Root — not five. A2 and B are untouched originals, reused as children of the new nodes around them rather than copied. And the old Root, A, A1 still exist, unchanged, pointed to by anything that was holding them before the edit — the edit built a new path to a new root; it did not touch the old one.

What goes wrong

  • Expecting the focus to stay where the edit happened. It doesn't — an edit climbs the whole trail and lands on the new root, trail empty, same as if the zipper had just been created. Treat the return value as "a new tree," not "my cursor, still at A1."
  • Assuming a step sideways is as cheap as a step up or down. This zipper's trail only remembers ancestors, not the siblings beside them. Moving to a different child means going up and back down by name or by condition, scanning that level's children — never a single "move right" step, because none is kept.
  • Forgetting the old tree is still there. Nothing was mutated, so a reference taken before the edit still sees the pre-edit shape. That's the structural sharing working as intended, not a bug — but code that edits and then re-reads the original variable expecting to see its own change will not.

Where this is used

Rewriting an AST without arbitrary jumps: walk down into the tree to a jump that needs restructuring, turn it into a conditional block, climb back out — each climb rebuilding only the handful of ancestors on that one path, every sibling subtree reused untouched. An AST with thousands of nodes and one jump somewhere inside it rebuilds a few nodes per fix, not thousands.
