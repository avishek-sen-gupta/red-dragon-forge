Fixpoints and worklists

How a program analysis handles loops: keep applying the rules until nothing changes.

The problem

You want to know, for every statement in a program, something that is true on every path that reaches it — which statements may have last written each variable, say. Straight-line code is easy: walk it top to bottom. A loop is not. The statement at the top of a loop can be reached from before the loop or from the end of its own body, and you cannot know what the end of the body looks like until you have walked the body, which starts at the top.

The intuition

Start with every statement knowing nothing. Visit statements one at a time. At each one, gather what its predecessors currently know, apply the statement's effect, and if the result is bigger than what the statement knew before, tell its successors to look again. Stop when nobody needs to look again.

That stopping point is a fixpoint: applying the rules once more would change nothing. It is reached because the facts only ever grow and there are finitely many of them. And it is the same answer whatever order you visit in — order changes how much work you do, not what you find.

The example

A loop whose body copies WS-A into WS-B, and a read of WS-B after the loop.



The facts here are, for each field, the set of statements that may have last written it. start stands for the value the field holds on entry. The statements are named the way cobble names them: paragraph, then position.

The rule



in(s)  = ⋃ out(p) for every predecessor p of s   (the entry also gets "start")

out(s) = transfer_s(in(s))

repeat: take s from the worklist; if out(s) grew, add s's successors

until the worklist is empty



Two properties make this terminate with one answer. Each transfer is monotone: more knowledge in never means less out. And the facts form a finite lattice: each field can be credited to at most every write in the program. Every change makes some set strictly bigger, so changes run out.



What goes wrong


    

  • Order is cost. First-in-first-out wanders out of the loop before the loop has settled, then has to redo everything after it once the loop changes. Reverse postorder — roughly, "a statement before its successors, the loop body before what follows the loop" — finishes the loop first. On cobble's largest program, changing order alone cut statement visits from about 107,000 to about 20,000, with an identical answer.
    • 

  • Budgets. A big program with many nested loops can still need a lot of visits, so a real analysis caps them. Stopping early gives facts that are missing some writes, never ones that are wrong: everything recorded was reached by a real path. Cobble publishes such a result and marks it unsettled.
    • 

  • Non-monotone rules break everything. If a transfer could shrink a fact, the loop could oscillate forever, and different orders could stop at different answers.
    •
