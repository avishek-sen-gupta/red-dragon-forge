Analyse, run and test COBOL, CICS, JCL and Db2 applications on a laptop, from unmodified source and real data, with deterministic execution.

The problem

Mainframe business logic is hard to read, run and change

Opaque

Decades of COBOL, CICS transactions, JCL job streams and Db2 access — spread across thousands of members, known mostly to the people who maintain it.

Testable only on the host

Running anything needs a mainframe region, datasets and a test window. Feedback takes days.

Risky to migrate

Migrations fail on undocumented behaviour: packed decimals, edit pictures, condition codes, pseudo-conversational state.
Three problems: it is hard to see what the system does, expensive to run it, and hard to show that a replacement behaves the same.
The approach

Three parts: analysis, interpreter, runtimes

CobbleStatic analysis: a knowledge graph of the whole system, call graphs, field-level dataflow, screens from source
→
RedDragonDeterministic interpreter: COBOL lowered to a universal IR and executed with byte-level memory
→
Forge runtimesCICS online, JCL batch and EXEC SQL / Db2, attached through extension points, not by changing the engine

The examples throughout use AWS CardDemo, an open-source mainframe credit-card system.

Order of the talk: analysis (Cobble) → engine (RedDragon) → online, batch and database runtimes (Cicada, Jackal, Squall) → results on a production estate → known gaps.

Analysing a codebase
without running it

Cobble reads COBOL, CICS, JCL and BMS source and builds a queryable model of the whole system, down to individual fields. The examples here are from CardDemo.

Cobble · dynamic call targets

Resolving dynamic XCTL targets across programs

Program → program XCTL from the graph. Solid: proven target. Dashed: candidate. Red: a candidate only the cross-program combine finds.
  1. Fixpoint, per program. Follows the values a program assigns itself — VALUE clauses, MOVEs, menu tables — to every XCTL PROGRAM(field).
  2. Combine, across programs. Links callers to callees and carries the COMMAREA bytes a caller hands over into the callee. That answers "return to whoever called me".

"Fully resolved" here means: the site's candidate set from the fixpoint alone already equals its set after the combine. 24 of 24 sites name at least one program even from the fixpoint alone; at 4 of them that set is missing the caller the program returns to, and the combine adds it — 3 rounds, 4 discovered links. Only 6 of the 24 are proven: one target and no reason for doubt. The rest are candidate sets — sound over-approximations, kept with their reasons (uninitialised, not-a-literal, unmodelled), so a candidate edge means "may transfer here", not "does". A subscripted target such as the menu table entry CDEMO-MENU-OPT-PGMNAME(WS-OPTION) names no single occurrence, so linking keeps the fixpoint's candidates and its doubt for it. Cost: the combine runs in about 1.4 seconds over the whole corpus, after the fixpoint.

Cobble · techniques

The analysis techniques behind these results

DataflowControl flowExecution
TechniqueHow Cobble uses itUse in reverse engineering
Monotone dataflow fixpointA worklist over CFG nodes on a byte-level lattice. Join is union; the lattice has finite height, so it terminates. A reverse-postorder sweep is the cheaper option.For any read, which statements could have set its value, across branches and loops, without running the program.
Alias model over byte extentsByte extents from the record layout (PIC, USAGE, OCCURS, REDEFINES). Reads match by may-alias (over-approximates); a write kills only what it must cover (under-approximates).A field written under one name and read under another stays connected: REDEFINES, group and child moves, reference modification.
Value sets with reasonsThe byte values a field can hold, and why there may be others (not-a-literal, inbound-linkage, uninitialised …). Once settled, the fixpoint and linking over-approximate: no real flow is dropped. The sampler under-approximates: everything it reports happened on some path.

Background for each technique is in docs/explainers: fixpoints.html, value-sets.html, byte-extents.html, reaching-definitions.html, reaching-conditions-slice.html and traversal-orders.html. Limits. The fixpoint does not track which PERFORM a paragraph was entered from: a performed paragraph is lowered once, and its RETURN edges go to every call site. Reaching conditions do match returns, but stop at 64 paths per node and report the nodes cut short. Arithmetic results keep their provenance but not their value, so a field set by COMPUTE or ADD reads as not-a-literal. In linking, when a caller passes the field that named the callee, the callee reads its own name in those bytes; that is how "return to whoever called me" resolves. Value sets hold at most 32 values. A fixpoint stopped by its cost cap is published as unsettled; by monotonicity everything it reports is still real.

Known gaps

What doesn't work yet

Engine

  • SORT / MERGE verbs not lowered
  • Arithmetic via floating point, not true fixed-point
  • SEARCH ALL is a linear scan
  • Some unhandled statements warn instead of failing

Batch (JCL)

  • Executes IEFBR14 and IDCAMS only — no SORT, IEBGENER, IEBCOPY, ICETOOL
  • IDCAMS: no VERIFY, LISTCAT, PRINT, DEFINE GDG
  • GDG generations, PDS members, DD concatenation, DCB, IF/THEN/ELSE

Online (CICS)

  • Temporary storage queues, RESETBR
  • SEND MAP options: CURSOR, ERASE, FREEKB
  • One terminal at a time; conversational (non-pseudo-conversational) programs
  • One task at a time

SQL & analysis

  • Dynamic SQL, CALL, indicator variables, full SQLCA
  • No dialect translation
  • Cobble: a few expression kinds or unresolved JCL symbols can drop a whole program or job from the graph
