The problem

The logic that runs the business is the hardest to touch

Opaque

Decades of COBOL, CICS transactions, JCL job streams and Db2 access — spread across thousands of members, documented mostly in people's heads.

Untestable off-host

Running anything means a mainframe region, datasets and a test window. Feedback loops are measured in days.

Risky to move

Migrations fail on behaviour nobody wrote down: packed decimals, edit pictures, condition codes, pseudo-conversational state.
Three pains stakeholders recognise: can't see it, can't run it cheaply, can't prove a replacement behaves the same.
The approach

See it. Run it. Prove it.

One application runs through the whole talk: AWS CardDemo, an open-source mainframe credit-card system.

Roadmap of the talk. Understand (Cobble) → engine (RedDragon) → run online, batch, database (Cicada, Jackal, Squall) → scale evidence → honest gaps.

04

The engine.

RedDragon compiles COBOL to a small universal IR and executes it on a deterministic VM — byte-faithful memory, packed decimals and EBCDIC included.

Everything online, batch and SQL runs on this one engine. No LLM is involved when source is complete.

The language as real programs use it

Data

PICTURE incl. numeric- and alphanumeric-edited · DISPLAY zoned, COMP, COMP-3, COMP-1/2 · EBCDIC · REDEFINES · RENAMES · OCCURS … DEPENDING ON · 88-levels · SIGN · JUSTIFIED · BLANK WHEN ZERO

Control & arithmetic

PERFORM (THRU, TIMES, UNTIL, VARYING … AFTER, inline) · EVALUATE · GO TO DEPENDING · ALTER · DECLARATIVES · COMPUTE · ROUNDED · ON SIZE ERROR

Strings, calls, files

STRING · UNSTRING · INSPECT · reference modification · CALL BY REFERENCE / CONTENT / VALUE · CANCEL · ENTRY · OPEN · READ · WRITE · REWRITE · START · DELETE over sequential, indexed and relative files

vendor/red-dragon/interpreter/cobol/features.py · docs/frontend-design/cobol.md · interpreter/cobol/lower_search.py

Engine · extension, not modification

CICS, SQL and JCL plug in through seams

DialectParserClaims EXEC CICS / EXEC SQL blocks at parse time
Extension lowering strategyTurns each EXEC statement into ordinary IR calls to registered builtins
CoprocessorSpecBundles parser + strategy + prepass; several compose into one program
RuntimeHow it attaches
Cicada · CICSCoprocessorSpec that owns execution — pseudo-conversational region around the VM
Squall · SQLCoprocessorSpec that composes with CICS; DCLGEN prepass; pluggable Db2 / SQLite backends
Jackal · JCLDriver around the VM — compiles each COBOL step, wires DDs through the file I/O seam, reads back the return code

The three runtimes never import each other — enforced by an import contract in CI. The core engine carries no CICS- or SQL-specific code.

interpreter/project/coprocessor_compile.py · cicada/cics/coprocessor.py · squall/squall/coprocessor.py · jackal/jackal/cobol_step.py · .importlinter
Nuance if asked: the core IR did grow a few language-neutral primitives extensions rely on (SUSPEND for conversational CICS, CALL_WITH_MEMORY). They are generic opcodes, not CICS code.

CICS · surface

The command surface CardDemo needs — and a loud failure for the rest

Program control

RETURN (TRANSID, COMMAREA) · XCTL · LINK · ABEND · START · RETRIEVE · HANDLE ABEND / CONDITION

Screens & files

READ · WRITE · REWRITE · DELETE · STARTBR · READNEXT · READPREV · ENDBR — KSDS with alternate indexes

System

ASSIGN · ASKTIME · FORMATTIME · INQUIRE · WRITEQ TD · RESP / NOHANDLE → EIBRESP

Not yet

Driving transactions from the screens themselves — today they run headlessly and screens are render-only · cursor position and attribute overrides on rendered screens · multiple concurrent terminals · raw 3270 datastream

By design

Any unsupported verb raises an explicit ABEND — never a silent skip. Every CICS behaviour reaches the engine as a registered builtin; the core VM is untouched.

What executes today — and what only parses

Executes end-to-end

  • SELECT … INTO with bound host variables — live Db2
  • Cursors: DECLARE / OPEN / FETCH loop / CLOSE — IBM cursor.sqb on Db2
  • COMMIT / ROLLBACK — IBM updat.sqb on Db2
  • CONNECT routing across two databases; real negative SQLCODEs
  • WHENEVER SQLERROR GO TO — branches on Db2's −204
  • INCLUDE SQLCA / DCLGEN; INSERT / UPDATE / DELETE (SQLite)

Parses, not yet executed

Honest gaps

What doesn't work yet

Engine

  • SORT / MERGE verbs not lowered
  • Arithmetic via floating point, not true fixed-point
  • SEARCH ALL is a linear scan
  • Some unhandled statements warn instead of failing

Batch (JCL)

  • Executes IEFBR14 and IDCAMS only — no SORT, IEBGENER, IEBCOPY, ICETOOL
  • IDCAMS: no VERIFY, LISTCAT, PRINT, DEFINE GDG
  • GDG generations, PDS members, DD concatenation, DCB, IF/THEN/ELSE

Online (CICS)

  • BIF DEEDIT, temporary storage queues, SYNCPOINT, RESETBR
  • SEND MAP options: CURSOR, ERASE, FREEKB
  • Headless only: screens render but can't yet be used to drive a transaction
  • One task at a time

SQL & analysis

  • Dynamic SQL, CALL, indicator variables, full SQLCA
  • No CICS–Db2 syncpoint coordination; no dialect translation
  • Cobble: a few expression kinds or unresolved JCL symbols can drop a whole program or job from the graph
